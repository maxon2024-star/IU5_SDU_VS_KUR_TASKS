# Лабораторная работа №6: Конвейеризация процессора и разрешение конфликтов (Pipelining & Hazards)

## 1. Введение и теоретическая база

В предыдущих лабораторных работах мы спроектировали **многотактный** процессор. Он разбивает выполнение одной команды на несколько стадий (Выборка, Декодирование, Выполнение), но делает это *последовательно*. То есть, процессор не начинает выборку новой инструкции, пока полностью не завершит выполнение текущей. Это приводит к простою аппаратных блоков: например, пока работает АЛУ, память команд (ROM) просто простаивает.

В этой лабораторной работе мы внедрим **Конвейеризацию (Pipelining)**. Это метод повышения пропускной способности процессора за счет параллельного выполнения фаз инструкций. Конвейер похож на сборочную линию на заводе: как только первая инструкция покидает стадию Выборки и переходит на стадию Декодирования, процессор сразу же начинает Выборку второй инструкции.

Однако параллелизм порождает проблемы — **конфликты (Hazards)**. В рамках задания со звездочкой вам предстоит реализовать один из индустриальных методов решения этих конфликтов.

Теоретической базой для выполнения работы служат материалы Модуля 2, Лекции 2 (Конвейеры, задержки).

**Цель работы:** Разделение Datapath на конвейерные стадии и реализация аппаратной защиты от конфликтов.

### 3.1 Структурная схема конвейера (Pipelined Datapath)

Обратите внимание на появление барьеров (`IF/ID` и `ID/EX`). Они работают как шлюзы (D-триггеры), которые "замораживают" сигналы ровно на один такт, чтобы передать их на следующую стадию синхронно.

```text
       [ СТАДИЯ 1: FETCH ]      [ СТАДИЯ 2: DECODE ]         [ СТАДИЯ 3: EXECUTE ]
                               |                            |
  +----+      +---------+      |      +--------------+      |      +---------+
  | PC |----->|   ROM   |==== IF/ID ==| Control Unit |==== ID/EX ==|   ALU   |---+
  +----+      +---------+      |      +--------------+      |      +---------+   |
                               |                            |                    |
                               |      +--------------+      |                    |
                               |      | Reg File (RF)|<==========================+
                               |      +--------------+      |    (Обратная связь)
                               |                            |

```

### 3.2 Шаблон конвейерного регистра (`pipeline_reg.v`)

Конвейерный регистр — это просто массив D-триггеров. Например, регистр между стадиями Выборки (IF) и Декодирования (ID) должен сохранять саму считанную инструкцию и текущее значение PC.

```verilog
module reg_if_id #(
    parameter INSTR_WIDTH = 16,
    parameter ADDR_WIDTH = 8
)(
    input  wire                   clk,
    input  wire                   rst,
    input  wire                   stall,     // 1 = Заморозить текущие значения
    input  wire                   flush,     // 1 = Очистить регистр (вставить NOP)
    
    // Входы со стадии Fetch (IF)
    input  wire [ADDR_WIDTH-1:0]  if_pc,
    input  wire [INSTR_WIDTH-1:0] if_instr,
    
    // Выходы на стадию Decode (ID)
    output reg  [ADDR_WIDTH-1:0]  id_pc,
    output reg  [INSTR_WIDTH-1:0] id_instr
);

    always @(posedge clk) begin
        if (rst || flush) begin
            id_pc    <= {ADDR_WIDTH{1'b0}};
            // Вставляем инструкцию NOP (Нет операции). Допустим, все нули - это NOP.
            id_instr <= {INSTR_WIDTH{1'b0}}; 
        end else if (!stall) begin
            // Если нет заморозки, передаем данные дальше по конвейеру
            id_pc    <= if_pc;
            id_instr <= if_instr;
        end
        // Если stall == 1, регистр просто сохраняет свое старое значение
    end

endmodule

```

> **Внимание:** Аналогично создается регистр `reg_id_ex`, который будет хранить прочитанные данные `read_data1`, `read_data2`, адреса регистров назначения и управляющие сигналы (`we`, `alu_ctrl`), выданные Control Unit'ом.

## 4. Задание со звездочкой: Разрешение конфликтов (Hazards)

В конвейере инструкции выполняются внахлест. Это порождает ситуации, когда одна инструкция зависит от результата другой, которая еще не успела завершиться. Вам необходимо реализовать блок разрешения конфликтов **строго в соответствии с вашим вариантом**.

### Вариант 1: Data Hazard (Базовый / Stall)

**Проблема:** Инструкция 2 (на стадии ID) пытается прочитать регистр, в который Инструкция 1 (на стадии EX) еще не успела записать ответ (RAW - Read After Write).
**Решение:** Написать модуль `hazard_unit`, который сравнивает адреса регистров. При совпадении он останавливает PC и `IF/ID` на 1 такт, давая первой инструкции закончить работу.

```verilog
module hazard_unit (
    input wire [3:0] id_rs1, id_rs2, // Регистры, которые мы ЧИТАЕМ на стадии ID
    input wire [3:0] ex_rd,          // Регистр, в который ПИШЕТ предыдущая команда (EX)
    input wire       ex_we,          // Разрешена ли запись на стадии EX?
    output reg       stall           // Сигнал заморозки
);
    always @(*) begin
        stall = 1'b0; 
        // Если команда на EX пишет в не-нулевой регистр, и этот регистр нужен нам сейчас
        if (ex_we && (ex_rd != 4'd0)) begin
            if ((ex_rd == id_rs1) || (ex_rd == id_rs2)) stall = 1'b1;
        end
    end
endmodule

```

### Вариант 2: Data Hazard (Продвинутый / Forwarding)

**Проблема:** Остановка конвейера (Stall) тратит такты впустую, снижая производительность.
**Решение:** Пробросить результат прямо с выхода АЛУ на входы АЛУ следующей инструкции, минуя регистровый файл. Для этого перед входами АЛУ ставятся мультиплексоры, управляемые модулем `forwarding_unit`.

```verilog
module forwarding_unit (
    input wire [3:0] id_rs1, id_rs2, // Что нужно АЛУ прямо сейчас
    input wire [3:0] ex_rd,          // Что выдает АЛУ на предыдущем шаге
    input wire       ex_we,          
    output reg       forward_a,      // 1 = взять проброшенный результат для входа А
    output reg       forward_b       // 1 = взять проброшенный результат для входа B
);
    always @(*) begin
        forward_a = 1'b0; forward_b = 1'b0;
        if (ex_we && (ex_rd != 4'd0)) begin
            if (ex_rd == id_rs1) forward_a = 1'b1;
            if (ex_rd == id_rs2) forward_b = 1'b1;
        end
    end
endmodule

```

### Вариант 3: Control Hazard (Flush при Jump)

**Проблема:** При команде перехода (Jump/Branch) следующая за ней инструкция *уже считана* в регистр `IF/ID` (стадия Fetch). Если переход происходит, эту ошибочно считанную инструкцию нужно "убить", иначе выполнится не тот код!
**Решение:** Написать логику, которая при декодировании JMP отправляет сигнал `flush` в конвейерный регистр `IF/ID`, превращая инструкцию в NOP (пузырек).

```verilog
// Внутри модуля Control Unit (или отдельного Branch Unit):
assign flush_if_id = is_jump_instruction; // Если текущая команда - JUMP, очищаем конвейер сзади

```

### Вариант 4: Load-Use Hazard (Специфичный конфликт)

**Проблема:** Даже наличие Forwarding (Вариант 2) не спасает, если данные читаются из RAM (инструкция `LOAD`). Данные из памяти достаются слишком поздно, чтобы пробросить их прямо в АЛУ.
**Решение:** Конвейер обязан затормозить (Stall) ровно на 1 такт, но **только** если предыдущая инструкция была `LOAD`.

```verilog
module load_use_hazard_unit (
    input wire [3:0] id_rs1, id_rs2,
    input wire [3:0] ex_rd,
    input wire       ex_mem_read,  // 1 = Предыдущая команда читает память (LOAD)
    output reg       stall
);
    always @(*) begin
        stall = 1'b0;
        if (ex_mem_read && (ex_rd != 4'd0)) begin
            // Если предыдущая команда читает память в нужный нам регистр - ждем 1 такт!
            if ((ex_rd == id_rs1) || (ex_rd == id_rs2)) stall = 1'b1;
        end
    end
endmodule

```
